## 2. Team goals

- Deliver a technical specification and API contract that another team can implement **without needing to ask us anything**.
- Implement the specification designed by the other team, and write a fair, useful evaluation of their documentation.
- Aim for a high grade (9/10 or higher).
- Make sure everyone participates equally and learns every part of the design process.

## 3. Roles and responsibilities

Each member owns one area of the work. Another member reviews that area before it counts as done.

| Role | Responsibilities | Owner |
| ---- | ---------------- | ----- |
| Product Owner / Requirements | Overview, target audience, MoSCoW feature list, user stories with measurable acceptance criteria. Confirms scope with the lecturer. | |
| Software Architect / Patterns | High-level architecture, package and class diagrams, design patterns and their justification. | |
| Process Analyst / Data Model | Business flows (sequence diagrams), data model with typed fields, enums and states. | |
| UI/UX Designer | Low-fidelity wireframes for all major use cases, screen transitions, a description of every button and panel. | |
| API Contract / Integrator / QA | API contract, events, error codes, traceability matrix, final integration of the document, "implementer's hat" review, evaluation of the other team's document. | |

All members can (and should) help in other areas when needed. Owning an area means being responsible for it, not working on it alone.

## 4. Communication

- **WhatsApp group:** day-to-day communication, quick questions and urgent notices.
- **Weekly meeting** (20–30 minutes, in person or online): review progress, solve blockers and plan the next week.
- **Response time:** within 24 hours on weekdays.
- If a member cannot attend a meeting or meet a deadline, they tell the team **in advance**.
- Important decisions (scope, architecture, naming) are written down in the group or in the shared document so nobody misses them.

## 5. Tools

- **Shared document:** Word / Google Docs, the official deliverable shared with the lecturer.
- **Diagrams:** draw.io, PlantUML or Mermaid, with one consistent style across the whole document.
- **GitHub:** repository for submissions, this agreement and, in the implementation phase, the code.

## 6. Workload and contribution

- We all commit to an equal contribution (about 20% each).
- Tasks are split at the start of each phase and recorded in writing (see `reparto.md`).
- If someone falls behind, we discuss it openly at the weekly meeting and rebalance tasks. The goal is to finish the work, not to blame anyone.

## 7. Quality rules

- **Common glossary:** entity, state, module and event names are agreed at the start and used identically in every section.
- **Four-eyes rule:** every section is reviewed by at least one member who did not write it.
- **No vague requirements:** every acceptance criterion has a concrete number or rule (no "fast", "several" or "secure" on its own).
- **Traceability:** every Must requirement can be traced to a pattern, a flow, a screen, an entity and an endpoint/event.
- Before submission, we run an "implementer's hat" review: we read the document as if we had to build it, and fix every open question.

### Implementation phase

- Nobody pushes directly to `main`. Every change goes through a Pull Request.
- Every Pull Request needs at least one approval from another member before merging.
- Requested changes in a review are addressed within 48 hours.

## 8. Deadlines

- Internal deadline: each section is finished **at least 2 days before** the official deadline, so there is time for review and integration.
- The final version of the document is frozen before the official submission deadline. No edits after that.

## 9. Conflict resolution

1. Disagreements are first discussed respectfully between the people involved.
2. If there is no agreement, the whole team discusses it at the next meeting and decides by majority vote.
3. If a problem continues (for example, repeated missed deadlines or lack of participation), the team will contact the lecturer.
